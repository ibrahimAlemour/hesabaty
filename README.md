# حساباتي – نظام كاشير وإدارة محل (SaaS متعدد المحلات)

تطبيق ويب (PWA) بسيط وسريع لأصحاب محلات اللحوم والخضار والدجاج والمواد الغذائية الصغيرة.
مبني بالكامل بـ **HTML + CSS + JavaScript Vanilla** بدون أي إطار عمل (React/Vue/Angular)، ويعمل من الهاتف والكمبيوتر، بالعربية RTL، والعملة الافتراضية الشيكل ₪.

المشروع الآن مُقدَّم كخدمة (SaaS) بقاعدة بيانات واحدة مشتركة لكل المحلات المشترِكة، مع **لوحة مدير عام منفصلة تمامًا** لإدارة المحلات والاشتراكات والدفعات. راجع **[القسم 11](#11-لوحة-المدير-العام-ونظام-saas-متعدد-المحلات)** لتفاصيل هذا الجزء تحديدًا.

## 2. تشغيل المشروع محليًا

المتصفحات تمنع `ES Modules` و `Service Worker` من العمل عبر `file://`، لذلك يجب تشغيل خادم محلي بسيط:

```bash
cd hesabaty
python3 -m http.server 8080
# أو: npx serve .
```

ثم افتح المتصفح على:

```
http://localhost:8080/index.html
```

عند أول تشغيل ستظهر شاشة **الإعداد الأولي (Setup Wizard)**: اسم المحل → العملة → منتجات مبدئية (مع خيار تحميل بيانات تجريبية) → إنشاء حساب صاحب المحل. بعدها تدخل مباشرة إلى لوحة التحكم.

## 3. طريقة إضافة منتجات وزبائن (باختصار)

**إضافة منتج:** المزيد ⟵ المنتجات ⟵ "+ إضافة منتج" ⟵ أدخل الاسم، التصنيف، الوحدة، سعر الشراء، سعر البيع ⟵ حفظ. يمكن تفعيل "اختصار سريع" ليظهر المنتج كزر كبير في شاشة البيع.

**إضافة زبون:** الزبائن ⟵ "+ إضافة زبون" ⟵ الاسم (والهاتف اختياري) ⟵ حفظ. يمكن أيضًا إضافة زبون جديد من داخل شاشة "بيع جديد" مباشرة عند اختيار الزبون.

**بيع سريع بدون زبون:** فقط لا تختر زبونًا (يبقى "زبون نقدي" افتراضيًا) وأكمل البيع كالعادة - هذا هو البيع السريع المطلوب في المواصفات.

## 4. إنشاء مشروع Supabase (اختياري)

التطبيق يعمل بالكامل بدون إنترنت وبدون Supabase منذ اللحظة الأولى (باستخدام IndexedDB). ربط Supabase اختياري لمن يريد نسخة سحابية/مزامنة بين أكثر من جهاز.

1. أنشئ حسابًا على [supabase.com](https://supabase.com) ثم مشروعًا جديدًا (اختر أقرب منطقة).
2. من **SQL Editor** نفّذ محتوى الملف `supabase/schema.sql` كاملاً (ينشئ كل الجداول + تفعيل RLS + السياسات).
3. من **Authentication → Providers** فعّل تسجيل الدخول بالبريد الإلكتروني (Email/Password).
4. أنشئ أول مستخدم (owner) من **Authentication → Users → Add user**، ثم أضف له صفًا في جدول `profiles` بنفس `id` مع `role = 'owner'`.
5. من **Project Settings → API** انسخ:
   - `Project URL`
   - `anon public key` (وليس `service_role` أبدًا)

---

## 5. ربط التطبيق بـ Supabase

1. افتح التطبيق ⟵ الإعدادات ⟵ قسم **"اتصال Supabase"**.
2. ألصق `Project URL` و `anon public key`.
3. اضغط **"اختبار الاتصال والتفعيل"**. عند النجاح يتحول التطبيق تلقائيًا لوضع `supabase` مع الاحتفاظ بكل بياناته المحلية.
4. من هذه اللحظة: كل عملية تُكتب محليًا (IndexedDB) فورًا **وفي نفس الوقت** تُرفع إلى Supabase؛ وإذا انقطع الإنترنت تُحفظ في **طابور مزامنة (Sync Queue)** وتُرفع تلقائيًا عند عودة الاتصال (بترتيب صحيح ودون تكرار، لأن كل عملية تحمل UUID فريدًا).
5. حالة المزامنة وعدد العمليات المعلّقة تظهر في نفس صفحة الإعدادات، مع زر "مزامنة الآن".

> ملاحظة أمان: الواجهة لا تستخدم إطلاقًا `service_role key`. الحماية الحقيقية للبيانات تتم عبر Row Level Security المفعّلة في `schema.sql`.

## 6. النشر على Cloudflare Pages

المشروع بالكامل ملفات ثابتة (Static)، لا حاجة لأي عملية Build:

1. ادفع المجلد `hesabaty/` إلى مستودع Git (GitHub/GitLab).
2. من لوحة Cloudflare ⟵ **Workers & Pages ⟵ Create ⟵ Pages ⟵ Connect to Git**.
3. اختر المستودع. في إعدادات البناء:
   - **Build command:** اتركه فارغًا
   - **Build output directory:** `hesabaty` (أو الجذر إن كان المستودع يحتوي المشروع فقط)
4. اضغط **Save and Deploy**. سيصلك رابط مباشر (`*.pages.dev`) يمكن تثبيته على الهاتف كتطبيق (PWA) فورًا.
5. عند كل تحديث للكود، ادفع (`git push`) وسيُعاد النشر تلقائيًا.

## 8. ميزات لم تُنفَّذ بالكامل / ملاحظات مستقبلية

- **PDF حقيقي**: تم استخدام صفحة طباعة نظيفة (Print-friendly) يمكن حفظها كـ PDF من نافذة طباعة المتصفح، بدل توليد PDF بمكتبة منفصلة (لتفادي تعقيد غير ضروري ووزن تحميل زائد على تطبيق يجب أن يعمل offline).
- **Row Level Security على مستوى الأعمدة** (مثل إخفاء `cost_price`/`total_profit` عن الكاشير على مستوى قاعدة البيانات): مطبّق حاليًا كإخفاء في الواجهة (client-side) فقط. RLS في `schema.sql` يقيّد الحذف والعمليات الحساسة (المصروفات، سجل التدقيق) على `owner` فقط، لكنه لا يخفي أعمدة بعينها ضمن جدول `sales`. يمكن إضافة `view` منفصلة للكاشير مستقبلاً إن احتاج المشروع ذلك.
- **إنشاء حساب محل جديد بضغطة واحدة من لوحة المدير**: يتطلب دالة خادمية آمنة تحمل `service_role key` (مثل Cloudflare Worker Function). حاليًا هذه الخطوة يدوية بسيطة عبر لوحة Supabase (موضّحة بالقسم 11.5).
- **إشعارات Push حقيقية** (تذكير بالديون، أو تنبيه المدير باشتراكات قاربت الانتهاء): لم تُطلب صراحة وليست ضرورية للنسخة الحالية.
- **مزامنة تعارضات (Conflict resolution) متقدمة** بين جهازين يعدّلان نفس الفاتورة أثناء انقطاع الإنترنت لكل منهما: النظام الحالي يعتمد "آخر كتابة تفوز" (Last Write Wins) عبر `upsert`، وهو كافٍ لصاحب محل واحد يستخدم جهازًا واحدًا أو جهازين بالتناوب، لكنه ليس Conflict-free Replicated Data Type متقدمًا.

كل الأزرار الموجودة في الواجهة فعّالة وتنفّذ عملها الحقيقي - لا توجد أزرار وهمية.

## 10. قابلية التطوير المستقبلي

- **الفصل الصارم بين الواجهة وقاعدة البيانات** (`database.js` كنقطة وصول وحيدة) يسمح بإضافة أي مصدر بيانات جديد (مثل REST API خاص) دون تعديل أي شاشة.
- **الأموال بالكامل بالأعداد الصحيحة (سنت/أجورة)** بدل الفاصلة العشرية، مما يمنع مشاكل التقريب الشائعة في تطبيقات المحاسبة المبنية بـ JavaScript.
- **الأرصدة والأرباح تُحسب دائمًا من السجل الخام** (المبيعات + الدفعات + المصروفات) لا من حقل مخزَّن، لذلك أي حذف/تعديل يصحّح كل الأرقام تلقائيًا دون Migration.
- **Audit Log + Soft Delete** جاهزان لأي متطلبات مراجعة أو استرجاع بيانات مستقبلية.
- **هيكل ملفات مسطّح وواضح** (وحدة واحدة = شاشة واحدة أو مسؤولية واحدة) يسهّل إضافة شاشات جديدة (مثل "الموردين" أو "الجرد") دون التأثير على الموجود.

## 11. لوحة المدير العام ونظام SaaS متعدد المحلات

### 11.1 الفكرة المعمارية

قاعدة بيانات Supabase أصبحت **مشتركة بين كل المحلات**، وليست قاعدة منفصلة لكل محل كما في النسخة الأولى. كل صف بجداول البيانات (زبائن، منتجات، فواتير...) مرتبط بعمود `shop_id`، وتضمن سياسات RLS أن كل محل **لا يرى ولا يكتب إلا بيانات نفسه فقط**، بينما حساب **Super Admin** يتجاوز هذا العزل ليرى كل المحلات من لوحة منفصلة تمامًا (`/admin`).

### 11.2 خطوة تنفيذ مطلوبة مرة واحدة (إن لم تُنفَّذ بعد)

نفّذ ملف **`supabase/schema_saas.sql`** كاملاً من SQL Editor (بعد `schema.sql` الأصلي). هذا الملف:
- ينشئ جداول `shops` و`subscriptions` و`subscription_payments` و`admin_settings` و`admin_audit_log`.
- يضيف `shop_id` لكل الجداول القديمة ويعزلها عبر RLS بالكامل.
- **يحوّل حسابك الحالي (owner) تلقائيًا إلى `super_admin`** وينقل أي بيانات اختبار سابقة إلى "محل تجريبي" منفصل حتى لا تُفقد.
- آمن لإعادة التشغيل لو احتجت تنفيذه أكثر من مرة.

### 11.3 لوحة المدير العام

الرابط: `https://<رابط موقعك>/admin/` (مثال: `hesabaty.<username>.workers.dev/admin/`)

- تسجيل الدخول بنفس حساب Supabase Auth تبعك (الذي أصبح `super_admin` تلقائيًا بعد تنفيذ `schema_saas.sql`).
- تطبيق منفصل تمامًا بملفاته وتوجيهه (لا يشاركه أصحاب المحلات، ولا رابط له من تطبيق المحلات نفسه).
- يعمل على الهاتف (Bottom Navigation) وعلى الكمبيوتر (شريط جانبي)، بنفس نظام التصميم.

**الوظائف المتاحة:**
- **الرئيسية**: عدد المحلات (الكل/نشط/معلّق/متأخر)، إجمالي الإيرادات المحصّلة، إجمالي المستحقات، ملخص إيرادات آخر 6 أشهر، المحلات القريبة من انتهاء اشتراكها.
- **المحلات**: بحث بالاسم/الهاتف، بطاقة لكل محل تُظهر حالته (نشط/منتهي/متأخر بالدفع/معلّق) بلون مختلف، **+ إضافة محل جديد** (ينشئ صف المحل وأول فترة اشتراك دفعة واحدة).
- **تفاصيل المحل**: بيانات المحل، الاشتراك الحالي، **تجديد/إضافة فترة**، **تسجيل دفعة** (نقدي/تحويل/أخرى + الفترة التي تغطيها)، **تعليق/إعادة تفعيل** بضغطة مع نافذة تأكيد، سجل كامل لكل الفترات والدفعات.
- **الإعدادات**: فترة السماح بعد انتهاء الاشتراك (أيام) قبل التعليق التلقائي، عدد أيام تنبيه اقتراب التجديد، نص رسالة التعليق التي يراها صاحب المحل، وسجل تدقيق لآخر العمليات الإدارية (من عمل ماذا ومتى).

**التعليق التلقائي**: عند فتح لوحة المدير، تُفحَص كل المحلات تلقائيًا (دالة `check_and_suspend_expired_shops` بقاعدة البيانات) وتُعلَّق أي محل تجاوز اشتراكه + فترة السماح دون تجديد. إن أردت فحصًا مجدولاً يوميًا حتى بدون فتح اللوحة، وتوفّرت إضافة `pg_cron` بمشروعك، فعّل السطر الموجود كتعليق بنهاية `schema_saas.sql`.

### 11.4 كيف يرى صاحب المحل التعليق

عند تعليق محل، يظهر لصاحبه ولموظفيه عند فتح التطبيق **شاشة توضيحية كاملة** بدل أي بيانات (🔒 "الحساب معلّق مؤقتًا" + نص التواصل اللي حدّدته من إعدادات لوحة المدير)، مع رسالة تطمين أن بياناته وفواتيره وديونه محفوظة بالكامل ولم تُحذف. بمجرد إعادة التفعيل من لوحة المدير، يعود الوصول فورًا بلا أي إجراء إضافي من صاحب المحل.

### 11.5 كيف تُضيف محلًا جديدًا (العملية الكاملة)

الإنشاء التلقائي لحساب دخول جديد يتطلب صلاحية `service_role` التي **يُمنع استخدامها من كود المتصفح لأي سبب أمني**، لذلك خطوة إنشاء حساب الدخول تبقى يدوية بسيطة (نفس ما فعلناه لحسابك الأول):

1. من لوحة المدير ← المحلات ← **+ إضافة محل جديد** ← عبّي بيانات المحل وسعر/مدة الاشتراك الأول ← احفظ.
2. من لوحة Supabase ← **Authentication → Add user** ← أنشئ بريد/كلمة مرور لصاحب المحل الجديد ← انسخ الـ **UID**.
3. من **Table Editor → profiles → Insert row**: `id` = نفس الـ UID، `name` = اسمه، `role` = `owner`، `shop_id` = معرّف المحل الذي أنشأته بالخطوة 1 (تجده بعنوان الصفحة `#/shops/<id>` أو من Table Editor → shops).
4. أعطِ صاحب المحل رابط التطبيق + بيانات الدخول. عند أول فتح: الإعدادات ← اتصال Supabase مملوءة تلقائيًا بنفس مشروعك (بفضل `js/saas-config.js`) ← يضغط **اختبار الاتصال والتفعيل** ← يسجّل خروج ويدخل ببريده وكلمة مروره ← جاهز.

> لإضافة زر "إنشاء حساب تلقائي بضغطة واحدة" مستقبلاً، الحل الآمن هو دالة خادمية (Cloudflare Worker Function) تحمل `service_role key` كسرّ محفوظ بالخادم فقط وتستدعي Supabase Admin API - خارج نطاق هذه النسخة.

### 11.6 الأمان والعزل

- كل الجداول (عدا `categories` المرجعية المشتركة) محمية بـ RLS تشترط `shop_id = my_shop_id()`، فلا يقدر أي محل يقرأ أو يكتب بيانات محل آخر حتى لو حاول تعديل الطلبات يدويًا.
- `is_super_admin()` و`my_shop_id()` دوال `SECURITY DEFINER` بمسار بحث ثابت لمنع أي استدعاء ذاتي لانهائي (نفس فئة الخلل اللي صادفناه وأصلحناه سابقًا في `is_owner()`).
- جداول SaaS نفسها (`shops`, `subscriptions`, `subscription_payments`, `admin_audit_log`) مقصورة بالكامل على `super_admin`، عدا قراءة محدودة لصاحب المحل لصف محله/اشتراكه فقط (لعرض حالة التعليق وتاريخ الانتهاء).
- كل عملية إدارية حساسة (إنشاء محل، تعليق، تفعيل، تجديد اشتراك، تسجيل دفعة) تُسجَّل في `admin_audit_log` مع اسم المدير والوقت والتفاصيل.
