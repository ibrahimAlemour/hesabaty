# مرجع سياسات RLS (Row Level Security)

توثيق موحّد للحالة **الفعلية النهائية** لكل سياسة RLS بقاعدة البيانات، بعد تطبيق كل من `schema.sql` ثم
`schema_saas.sql` بالترتيب (كما هو مطلوب فعليًا بالنشر - راجع `README.md`). هذا الملف **مرجع قراءة فقط**،
لا يُنفَّذ بالقاعدة ولا يُستبدَل به أي من ملفي السكيما.

> **لماذا هذا الملف ضروري**: `schema_saas.sql` يحتوي عدة مراحل ترقية متتالية بالملف نفسه (يُلاحَظ من
> تعليقات الأقسام المرقّمة فيه)، وبعضها يُسقط (`drop policy`) ويُعيد تعريف (`create policy`) السياسة **نفسها**
> أكثر من مرة - أبرزها القسم 23 الذي قيّد كل عمليات الكتابة بـ`is_owner()` بعد أن كانت مفتوحة لأي عضو بنفس
> المحل (كاشير ضمنًا). القراءة المباشرة للملف بالترتيب من الأعلى للأسفل تُعطي انطباعًا خاطئًا بأن السياسة
> الأقدم هي الفعّالة؛ **الفعّال دائمًا هو آخر `create policy` بنفس الاسم بالملف**. هذا المرجع يلخّص الناتج
> النهائي فقط حتى لا يُضطر أي مطوّر لإعادة هذا التتبّع اليدوي بنفسه.

## 1. الدوال المساعدة (Security Definer)

| الدالة | التعريف | ملاحظة |
|---|---|---|
| `is_owner()` | `role = 'owner'` لصاحب الجلسة الحالية | **لا تفحص `shop_id` بنفسها إطلاقًا.** أي سياسة تستخدمها بمفردها (بدون `and shop_id = my_shop_id()` بجانبها) تمنح الكتابة لأي صاحب محل عبر *كل* المحلات، لا محله فقط. هذا كان ثغرة أمنية حقيقية أُصلحت (راجع §4) بإضافة الشرط لكل سياسة كتابة كانت تفتقده - **وليس** بتعديل الدالة نفسها. أي سياسة جديدة مستقبلًا يجب أن تجمع الشرطين معًا يدويًا. |
| `is_super_admin()` | `role = 'super_admin'` لصاحب الجلسة الحالية | يُستخدم فقط من حساب لوحة المدير العام (`admin/`)، لا من تطبيق المحل. |
| `my_shop_id()` | `shop_id` من صف `profiles` لصاحب الجلسة الحالية | أساس كل عزل بين المحلات. `security definer` + `search_path` ثابت لمنع أي استدعاء ذاتي خطير. |
| `check_and_suspend_expired_shops()` | تعلّق كل محل تجاوز اشتراكه + فترة السماح (`admin_settings.grace_period_days`) | تُستدعى من لوحة المدير عند التحميل؛ غير مجدولة تلقائيًا بـ`pg_cron` إلا إن فُعِّل ذلك يدويًا. |
| `increment_shop_sms_segments()` | تزيد عدّاد رسائل SMS المستهلَكة لمحل معيّن | تُستدعى فقط من `worker.js` بمفتاح `service_role` (يتجاوز RLS)، لا من عميل المتصفح. |

## 2. القاعدة العامة بكل الجداول "المعزولة"

كل جدول أعمال (غير `shops`/`subscriptions`/`admin_*`) يتبع نفس النمط:

- **SELECT**: `shop_id = my_shop_id() or is_super_admin()` - أي عضو بالمحل (owner أو cashier) يقرأ، والمدير العام يقرأ كل شيء.
- **INSERT**: `shop_id = my_shop_id()` فقط، أو `(shop_id = my_shop_id() and is_owner())` للجداول المالية/الحساسة - راجع الجدول أدناه لكل حالة بعينها.
- **UPDATE/DELETE**: نفس منطق INSERT تقريبًا، غالبًا مقيّد بـ`is_owner()` إضافة لـ`shop_id`.

**القاعدة الفعلية بعد إصلاح §4**: الكاشير (دور `cashier`) يقدر **فقط** يقرأ (SELECT) بيانات محله؛ أي
كتابة (INSERT/UPDATE/DELETE) على أي جدول أعمال تتطلب `is_owner()` - **لا استثناء**، حتى لو كانت الواجهة
تُخفي الزر عن الكاشير، فقاعدة البيانات نفسها ترفض الطلب لو استُدعي مباشرة (مثل `fetch` من console المتصفح).

الجداول. أُدرجت الحالة القديمة هنا فقط توضيحًا لنمط "تعريفين متتاليين" المتكرر بالملف (راجع التنبيه بالأعلى).

## 4. التخزين (Supabase Storage - سلة `attachments`)

السلة **غير عامة** (`public: false`). كل عمليات `storage.objects` (SELECT/INSERT/UPDATE/DELETE) مقيّدة
بشرط واحد: `bucket_id = 'attachments' and (storage.foldername(name))[1] = my_shop_id()::text` - أي أن أول
مجلّد بمسار الملف **يجب** أن يطابق `shop_id` الحالي. هذا يعتمد كليًا على الالتزام بمسار الرفع المتّبع بالتطبيق
(`{shop_id}/{entity_type}/{entity_id}/{filename}` - راجع `uploadAttachment` بـ`js/attachments.js`)؛ أي كود
مستقبلي يرفع لمسار لا يبدأ بـ`shop_id` الصحيح سيُرفض من الاستعلام، لا من الواجهة.

## 5. فجوات معروفة ومؤجَّلة عمدًا (ليست أخطاء، بل قرارات ثقة واسعة توسّع نطاق super_admin)

هذه النقاط ظهرت أثناء بناء هذا المرجع ولم تُعالَج بهذه الجولة (فئة "الأمان والموثوقية" لم تكن ضمن نطاق
العمل المطلوب حاليًا) - تُترك هنا موثّقة بدل أن تُكتشف بالصدفة لاحقًا:

- **`is_super_admin()` يمنح قراءة وكتابة كاملة على بيانات كل المحلات التجارية** (`sales`, `customers`,
  `products`, `expenses`...) لا فقط جداول SaaS الإدارية (`shops`/`subscriptions`). أي حساب بدور
  `super_admin` يقدر فعليًا يعدّل بيانات بيع/زبائن أي محل مباشرة عبر REST API بمفتاح anon، لا فقط عبر
  لوحة الإدارة. هذا اتساع ثقة متعمّد (ليسهل الدعم الفني)، لكنه غير مسجَّل بأي `audit_log` تلقائي عند حدوثه.
- **لا عزل تخزين منفصل بين تطبيق المحل ولوحة الإدارة**: كلاهما يستخدمان نفس مشروع Supabase/مفتاح anon
  العام، ويفترقان فقط بمنطق التطبيق (دور المستخدم). لا قيد RLS إضافي يمنع تسريب مسار إداري عبر الواجهة
  العادية بالخطأ مستقبلًا.
- **لا توجد سياسة DELETE على `profiles`**: حذف حساب مستخدم (كاشير أو غيره) يتم فقط عبر Worker بمفتاح
  `service_role`، وهذا مقصود (حذف Supabase Auth user يتطلب هذا المفتاح أصلًا) - لكنه يعني أن أي استعلام
  حذف مباشر من العميل سيُرفض دائمًا بصمت دون تفسير بسياسة RLS نفسها.

## 6. ترتيب التنفيذ المطلوب (تذكير)

```
1. supabase/schema.sql        -- السكيما الأصلية + أول نسخة RLS (محل واحد فقط، بدون shop_id)
2. supabase/schema_saas.sql   -- يرقّي كل شيء لعزل متعدد المحلات، ويحتوي كل الإصلاحات اللاحقة بنفس الملف
```

لا يوجد ملف SQL ثالث حاليًا؛ أي سياسة جديدة مستقبلًا تُضاف كقسم جديد بنهاية `schema_saas.sql` (بنفس نمط
الأقسام المرقّمة الموجودة)، ويجب تحديث هذا المرجع بالتوازي معها.
